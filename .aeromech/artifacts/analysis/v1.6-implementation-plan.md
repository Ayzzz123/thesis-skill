## Phase 3 — Orchestrator 核心：路由 / Agent Loop 集成 / Failure Recovery / Resume

1. **`scripts/thesis_orchestrator.py`**（唯一入口 `python thesis_orchestrator.py <root> <status|advance|resume|gate>`）：
   - `status`：读 state+checkpoint+research_context+qa_state → 当前阶段/已完成任务/未完成任务/下一步（§六恢复判定的实现；禁止从 S1 重启，除非 checkpoint 链为空）。
   - `advance`：前置校验（state.md §3/§5 + §17.1 v1.5 门禁 + **§十三 Feasibility Gate：S7 前 feasibility 必须 ≠ INFEASIBLE，否则停留本阶段**）→ 落 checkpoint → 迁移。
   - Agent Loop 集成：调 `research_agent_loop.run(root)`（subprocess，解析 loop-log json），终态映射：PASS* → 放行并记 checkpoint；PASS_WITH_HUMAN_REVIEW → 记 state `open_issue(queue)` + 指向 human-review-queue.yaml；BLOCK → 进 Failure Recovery。
   - **Failure Recovery**（指令 §七）：以 diagnosis 的 issue_type/disposition/severity 分类 → `retry`（脚本/环境类 ERROR、rc≠0 非内容码，最多 n 次）/ `repair`（auto disposition → research_repair execute 后重入本阶段）/ `rollback`（设计/方法/范围类 → state.md §8 映射 revert + reason+issue_id）/ `human_review`（queue 类 → NHR 队列，不代签）/ `block`（Critical integrity → 停，等人工）。策略表是数据不是 if-else 硬编码题目。
   - Resume 验证：恢复后已存在且 hash 未变的产物不重跑（checkpoint artifacts 对比）；需重跑的=失败阶段+其下游受影响 QA。
2. 测试：`test_orchestrator`、`test_resume`（写→中断→重载，成果不丢）、`test_failure_recovery`（五策略各至少一例，用 fixtures 植入对应错误）、`test_stage_routing`、`test_agent_loop_integration`（假 loop 终态→正确回退/停留，复用 v1_5 fixtures 的缺陷项目）。
3. commit：`v1.6.0: add thesis orchestrator with checkpoint recovery` / `v1.6.0: integrate agent loop and failure recovery`。

## Phase 4 — 统一文档构建 + Figure 接口 + Delivery Gate 聚合

1. **`scripts/figure_iface.py`**：定义主线唯一依赖的 Provider 契约（与指令 §二十同名）：
   ```python
   plan_figures(root) -> FigurePlan      # 读 artifacts/figures/figure-plan.md(+figures.yaml) 的机读化清单
   generate_figure(root, spec) -> Path   # 委派 provider；rc/FIGURE_ERROR 语义不变
   validate_figure(root, png) -> Status  # 封装 graph_quality_qa/figure_table_qa 单项调用
   ```
   本地默认适配器：render_mermaid.py + 项目 gen 脚本（经 plan 中的 script 字段调用）+ 现有 QA；`--provider` 可切换到协作者实现（UNKNOWN 契约，见 §接口风险）。**不 import 协作者代码、不建 Figure Engine 副本。**
2. **`scripts/thesis_build.py`**（统一 Thesis Build Pipeline / 文档链 runner）：
   - 输入：state + research_context + school-format.yaml + 项目**内容契约文件** `.aeromech/build-contract.yaml`（章节清单、图映射 FIG→png、表、封面字段、前后件——把各项目 build_docx_*.py 里的数据部分抽出为数据）。
   - 通用组装：TEMPLATE_FIDELITY 与 FORMAT_RECONSTRUCTION 双模式，复用 template_fidelity/docx_engine 原语；输出 毕业论文.docx/.pdf。
   - 链 runner：build → update_toc → cover_fidelity --restore → repaginate_tables → export_pdf → QA manifest 全链 → finalize_metadata，**每步 rc+报告落 qa_state**，顺序违例（如跳过 repaginate）不可能发生（代码固定顺序）。Word COM 步骤失败→ERROR(env) 分类。
   - 迁移验证：先用 test-3.0（模板型）与 test-5.0（重建型）跑通统一构建器与旧 builder 的产物做 QA 等价（tf/pdf_qa 全绿）——证明"新论文不再手写 builder"。
3. **`scripts/delivery_gate.py`**：聚合器。读 qa_state 中全部 QA 报告 + RQG + loop 终态 + 双人工队列裁决状态 → 五态终局（PASS/PASS_WITH_WARNINGS/PASS_WITH_HUMAN_REVIEW/BLOCK/ERROR；item 级沿用七态词表）→ `artifacts/qa/delivery-gate-report.md` + state 记录 + 退出码 0/1/2/3 惯例。缺任一必跑 QA → ERROR（不得静默放行，堵 false-pass）。
4. 测试：`test_document_pipeline`（两模式各一例，tempfile 项目出 docx；PDF 导出 COM 步骤 mock/skip 标注 SKIPPED_WITH_REASON）、`test_delivery_gate`（六态输入组合→五态输出矩阵）。
5. commit：`v1.6.0: add unified thesis build pipeline` / `v1.6.0: add figure provider interface` / `v1.6.0: add delivery gate aggregator`。

## 风险与决策点

- **R1 协作者分支 UNKNOWN**：契约先行（P4 只依赖三函数签名 + figure-plan 机读格式），其分支出现后做 adapter 对接，主线不等。
- **R2 Word COM 环境**：回归/test-8.0 需本机 Word；runner 把 COM 失败记 ERROR(env) 并明确披露，不伪 PASS。
- **R3 范围控制**：若某 Phase 暴露既有稳定模块必须改动，停下评估（最小修改+回归代价），不顺手重构。
- **R4 体量**：P6 冷启动是最大单项（新题目+新材料+四断点），预留独立会话段；中途每小步 commit（§25 纪律）。
