# AeroMech Thesis — v1.5.0 实施建议（基于第一阶段审计，未执行）

## 0. 对旧计划的判断（任务书第十二条要求）

原 v1.5 计划（Research Design Registry / Method Selection / Feasibility Gate / Claim Strength /
Diagnosis / RCA / Repair Plan / Auto Repair / Agent Loop / Quality Score / Coherence /
Quantitative Consistency / Scope Control / Human Review Loop）**并未过时，但已被前置完成**：
gap-analysis（2026-09-12）列出的 MISSING 1~8 全部已落地为代码+测试文件+规则书。
因此 v1.5 的正确剩余工作不是"开发"，而是：**验证 → 修复 → 集成 → 端到端 → 发布**。
直接按旧 Prompt"从零开发" = 重复劳动；直接宣布"已完成" = 未经测试的发布（违反项目自身
"任何功能必须先实现并通过测试，再更新 README" 的纪律，README.md 末节明文）。

原设计合理性复查结论：
- 合理保留：注册表驱动 + 白名单自动修复 + NHR 分流 + Critical 不被总分掩盖——与 v1.4.1
  状态模型同构，复用良好，无需改架构。
- 需要小调（不推翻）：① quality score 的 Citation 维必须接 RQG-12 或明确移除该维
  （恒 100 的维度是"看起来有实为无"，比缺一个维度更糟）；② recompute 的 shell=True
  需要在文档声明信任边界，或改为仅接受受控白名单命令形态；③ diagnosis 引用不存在的
  §13/§24 条款号——补一节"条款映射"或改引用，恢复可追溯性。
- 风险过高项（延后/降级）：暂无。Auto Repair 白名单本身设计保守（仅 4 操作、全留痕、
  禁止项硬编码策略拒止），可放心验证启用。

   IDENTICAL 基线。**这是同步风险的结构性对冲，先于一切。**

5. 产出 tests/v1_5/v1.5-run1-report.md（格式对齐 v1_4_1 报告）。

## Phase 3 — test-7.0 端到端 + 发布 v1.5.0

1. test-7.0 设计（按 gap-analysis §3.9 规格，建议加严）：
   - 新题目（与 1.0~6.0 不重复，建议"航空发动机孔探伤检测与维修决策"或同类）；
   - 3 RQ / 1 主方法+2 辅助 / ≥5 证据 / 模拟数据集 / ≥2 CALC / ≥3 Claim / ≥3 Conclusion /
     ≥2 图 ≥2 表——全流程 S1→S9 + 交付链；
   - **植入 5 类缺陷 + 1 冲突**，每类一个且可判定：①RQ 方法需求不满足（needs⊄provides）
     ②弱证据强断言（ES1×C4）③摘要数字漂移（0.5%~10% 带）④scope creep（excluded 项正文≥2次）
     ⑤无标签模拟数据集；冲突=两条文献数值矛盾→必须 CONFLICT+pending/NHR；
   - 期望：diagnosis 全部命中（19 类中 ≥5 类）；auto 修复仅白名单内操作发生且留痕；
     设计/方法/冲突类走 queue 不自动修；终态 PASS_WITH_HUMAN_REVIEW→人工裁决 ok→PASS；
   - 交付链 QA 全绿（tf/cover/pdf/RQG/loop）→ 毕业论文.docx/pdf；
   - 同时跑一次 v1.4.1 全量回归（v1_4/v1_4_1/test_a/test_b）确认无破坏。
2. 发布联动：CHANGELOG 补 v1.5.0 条目（新增/修复/门禁变更/兼容声明）；SKILL.md 版本行、
   README §11 三处同改；sync.py --check=IDENTICAL + test_dev_install_sync 全绿后才算发布完成。

   loop-log 的 why 字段是审计抓手。
